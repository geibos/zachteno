# Design

## Context

Способ оценки вопроса сейчас задаётся одним полем `kind` (`single`, `multiple_all`, `multiple_any`, `free_text`). Оно лежит в `questions.kind` как `text` с безымянным CHECK (`questions_kind_check`, миграция `20261013000002_content.sql`). Подсчёт живёт в `domain/src/scoring.rs`:
- `base_score` даёт W или 0;
- `penalties` складывает штрафы отмеченных неверных вариантов;
- `max_score` — сумма весов;
- `attempt_score` обрезает сумму нулём.

Максимум за вопрос нигде не хранится и не отдаётся: разбор попытки, таблица результатов, статистика и антифрод сравнивают балл с весом.

Студенту при прохождении отдаётся только `Choice {Single, Multiple, FreeText}` (`attempts/runner.rs`), без веса и режима.

## Goals / Non-Goals

**Goals:** частичное начисление в двух режимах; корректный максимум вопроса везде, где показан балл; отрицательный балл попытки.

**Non-Goals:**
- пересчёт уже сданных попыток;
- баллы за отдельные верные варианты (разный «вес» вариантов);
- импорт вопросов из таблиц.

## Decisions

- **Режим оценки — новые значения `kind`, а не отдельное поле.** Добавляются `multiple_each` («балл за каждый верный») и `multiple_fraction` («доля верных»). Владелец продукта попросил один селектор для всех способов, а `kind` уже и есть этот селектор. В БД, API и клонировании это одно значение, отдельное поле `scoring_mode` понадобилось бы согласовывать с `kind` везде. Альтернатива `partial: bool` + `partial_mode` отвергнута: она даёт недопустимые сочетания, например `single` + `partial`.
- **Формулы — в `ScoredQuestion::score`, максимум — в новом `ScoredQuestion::max_score()`.**
  - `multiple_each`: `W × c + P`, максимум `W × C`.
  - `multiple_fraction`: `W × c / C + W × P / N`; при `N = 0` второе слагаемое равно 0. Максимум `W`.
  - Остальные режимы считаются как раньше.

  Функция `max_score(questions)` становится суммой `question.max_score()`.
- **Штраф в двух новых режимах понимается по-разному, и это осознанно.** В «балл за каждый верный» штраф вычитается как есть, в баллах. В «доля верных» он нормирован: `W × штраф / N`. Владелец продукта подтвердил это 19.10.2026. Поэтому подпись поля штрафа в редакторе зависит от режима. По умолчанию в обоих режимах штраф 0 (`default_penalty`).
- **Округление до 2 знаков (половина — от нуля) — в домене, в `score`.** Раньше все баллы были суммами чисел с двумя знаками и округления не требовали. Дробный режим даёт W/3, а `answers.score numeric(8,2)` округлил бы его молча, и сумма в `attempts.score` разошлась бы с суммой строк. Округлив балл вопроса до суммирования, получаем одно и то же число в ответе, в попытке и в отчётах. Для старых режимов результат не меняется.
- **Нижняя граница попытки снимается во всём продукте.** `attempt_score` больше не делает `max(0)`. Так решил владелец продукта: опасный ответ с большим штрафом должен утягивать итог в минус. CHECK-ограничений на знак в БД нет, `final_score` и отчёты с отрицательными числами уже работают (`formatScore`, числовая сортировка).
- **Максимум вопроса отдаётся явно.** Добавляется поле `max_score`:
  - в `ReviewQuestion` (разбор попытки);
  - в `ColumnHeader` (таблица результатов теста). Фронт берёт максимум колонки из него, а не из `weight`.

  Статистика (`reporting/stats.rs`) считает «полностью верный» как `score >= question.max_score()`.
- **«Ошибка» в антифроде — ответ ниже максимума вопроса.** `MATCHING_MISTAKES` сейчас считает ошибкой `score <= 0`. При частичном начислении 2 из 3 тогда не было бы ошибкой, и одинаковые неполные ответы двух аккаунтов не совпали бы. Переходим на `score < max`. Для одиночного выбора, «только все» и «хотя бы один» с штрафами по умолчанию результат тот же. Это моё решение, требование антифрода («одинаковые наборы ошибок») по смыслу не меняется.
- **Подсказка студенту — булево `partial_credit` в вопросе попытки.** `Choice` по-прежнему управляет видом (радио или галочки) и не меняется. Флаг говорит только о способе оценки и не раскрывает ни правильности, ни веса. Текст подсказки: «Выберите все подходящие варианты. Засчитывается частично: балл за каждый верный, за неверные может сниматься.»
- **Селектор в редакторе остаётся сверху, рядом с весом** (`QuestionEditor.svelte`, сейчас уже первая строка формы). Новые пункты добавляются в `KIND_LABELS` в порядке:
  - «Один ответ»;
  - «Несколько: только все верные»;
  - «Несколько: хотя бы один верный»;
  - «Несколько: балл за каждый верный»;
  - «Несколько: доля верных»;
  - «Свободный ответ».

  Справа от веса показывается «макс. за вопрос: X»; для `multiple_each` значение пересчитывается при отметке верных. Подсказка `KIND_HINTS` описывает формулу режима.
- **Процент считается на сервере**, в домене (`scoring::percent`, `scoring::final_percent`), и отдаётся числом-строкой рядом с баллом: в разборе, на панели студента, в строках таблицы результатов, в сводной таблице и в CSV. Один источник правила вместо копий во фронтенде и экспорте. Итоговый процент «средней» политики — среднее процентов попыток, а не итоговый балл, делённый на какой-то максимум: при случайной выборке вопросов максимумы попыток могут различаться. Это моё решение. Для «лучшей» берётся процент той же попытки, что выбрана для итогового балла.
- **Миграция** удаляет `questions_kind_check` и создаёт CHECK с шестью значениями. Откат — обратная миграция, которая проходит только при отсутствии вопросов новых видов.

## Risks / Trade-offs

- [Снятие нижней границы меняет итоги будущих попыток в существующих тестах со штрафами] → уже сданные попытки хранят свой балл и не пересчитываются. Изменение заметно только на новых сдачах, в proposal оно помечено как BREAKING.
- [Чтение неизвестного `kind` молча превращается в `free_text` (`model.rs`, `parse(..).unwrap_or(FreeText)`)] → новые значения добавляются в `parse` вместе с enum, тест разбора всех `as_str` проверяет обратимость.
- [Подписи штрафа в двух режимах означают разное] → подпись и подсказка поля зависят от режима, сценарии в спеке фиксируют оба правила.
- [Пропорциональный режим даёт дроби: 0.33 + 0.33 + 0.33 = 0.99, а не 1] → принимаем; так работают все системы с округлением по вопросам, а итог совпадает с суммой видимых чисел.

## Migration Plan

1. Миграция CHECK применяется разовым сервисом `migrate` при выкатке. Старый код с новыми значениями не сталкивается: до выкатки их никто не пишет.
2. Существующие вопросы не переводятся в новые режимы. Тест «Теоретический экзамен — итоговый тест 2026» пока остаётся в «только все» (решение владельца продукта 19.10.2026).
3. Откат: предыдущий образ `app`. Если вопросы новых видов уже созданы, сначала переключить их на `multiple_all`, потом откатывать миграцию.
