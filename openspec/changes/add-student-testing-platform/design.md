# Design

## Context

Проект пустой: кода, спецификаций и инфраструктуры нет. Мотивация описана в `proposal.md` (раздел Why), требования — в `specs/*`. Основной стек владельца — Rust. Ожидаемый масштаб: сотни, максимум тысячи студентов. Пиковая нагрузка возникает, когда поток синхронно начинает тест: сотни одновременных попыток. Время для пользователей — МСК. Команда маленькая, поэтому простота эксплуатации важнее горизонтального масштабирования.

## Goals / Non-Goals

**Goals:**
- Один развёртываемый артефакт приложения: бэкенд вместе со статикой фронтенда.
- Доменная логика (оценивание, сроки, политики показа, правила навигации, уровни связей антифрода) — в чистых функциях с исчерпывающими unit- и property-тестами.
- Сохранность ответов и честность сроков: сервер — единственный источник истины.
- Возможность добавить второй экземпляр приложения без переписывания. Сам второй экземпляр в MVP не поднимаем.

**Non-Goals:**
- Микросервисы, отдельный брокер сообщений, Redis в MVP.
- SSR и SEO: кабинеты закрыты, публичных страниц для индексации нет.
- Мобильные приложения: только адаптивный веб.
- Всё из раздела Out of scope в `proposal.md`.

## Decisions

### D1. Модульный монолит на axum

Cargo workspace в `backend/`:
- `domain`: чистая логика без ввода-вывода. Оценивание, расчёт срока попытки, политики показа, правила навигации, перемешивание по seed, веса и уровни антифрода.
- `app`: axum-сервер, sqlx-репозитории, фоновые задачи, CLI на clap. Подкоманды: `serve`, `create-superuser`, `migrate`.

Внутри `app` код разделён на модули по capability: `auth`, `access`, `authoring`, `streams`, `attempts`, `reporting`, `antifraud`, `audit`, `ops`.

Альтернатива — отдельные сервисы. Отклонена: для такого масштаба это лишняя сложность в эксплуатации, а нужны общие транзакции (например, сохранение ответа вместе с блокировкой теста).

### D2. Фронтенд: SvelteKit + adapter-static, Tailwind, shadcn-svelte

SPA собирается в статику с fallback на `index.html`. В release-сборке статика встраивается в бинарь через `rust-embed`, в dev отдаётся Vite-сервером через прокси. Контракт API описывается OpenAPI из кода через `utoipa`, TypeScript-типы генерируются `openapi-typescript`, клиент — `openapi-fetch`. Проверка в CI: после генерации в рабочем дереве не должно остаться изменений.

Альтернативы:
- htmx + Askama. Даёт один язык, но редактор вопросов (варианты-картинки, перестановка, закрепление) и раннер с офлайн-повтором пришлось бы собирать на Alpine — хуже поддерживается.
- Leptos. Против него долгая сборка, бедная библиотека компонентов и сложности с гидратацией.

Так решили по итогам ревью трёх моделей и по выбору владельца.

### D3. PostgreSQL — единственный источник состояния

- Первичные ключи — UUIDv4: они же публичные идентификаторы, непредсказуемые, порядковых номеров в API нет.
- Токены ссылок (приглашения, доверенная регистрация, задание пароля, сброс пароля, подтверждение email, сессии): 256 бит из ОС-генератора, base64url. В базе хранится только SHA-256 токена, сравнение — по хешу.
- Время хранится как `timestamptz` в UTC. Перевод в МСК (`Europe/Moscow`) — только на границах ввода и вывода.
- Деньги не считаем, но баллы считаем в `rust_decimal` и храним в `numeric(8,2)`: веса и штрафы двузначные, `f64` дал бы ошибки округления.

### D4. Пароли и сессии

- Argon2id (крейт `argon2`): m = 64 МиБ, t = 3, p = 1, соль 16 байт на пароль. Перец передаётся как параметр `secret` Argon2 (`Argon2::new_with_secret`). Хеш хранится PHC-строкой, рядом — колонка `pepper_version`.
- Перцы задаются в конфиге списком `{version: secret}`, активный — последний. При входе со старой версией перца или с устаревшими параметрами пароль перехешируется.
- Хеширование — на `spawn_blocking` за семафором: не больше N одновременных хешей, где N = число ядер. Без семафора 64 МиБ на хеш открывают дорогу DoS по памяти потоком логинов.
- Список распространённых паролей (топ-100k из SecLists) встроен в бинарь и проверяется при регистрации и смене пароля. Проверку по HIBP не делаем: это внешний вызов и утечка метаданных.
- Ограничение входа: in-memory GCRA по IP и счётчик неудач в строке пользователя для нарастающей задержки. При втором экземпляре счётчик по IP переезжает в PostgreSQL.
- Сессии хранятся в собственной таблице `sessions`: хеш токена, пользователь, `last_seen_at`, user-agent, IP. Cookie `__Host-session` с `HttpOnly; Secure; SameSite=Lax; Path=/`.
- CSRF: для небезопасных методов требуется `Content-Type: application/json` и проверяется `Origin` (должен совпадать с хостом). Вместе с SameSite этого достаточно для SPA на том же origin. Альтернатива — double-submit токен — проще не становится.

### D5. OAuth: трейт `OAuthProvider`, первая реализация — Яндекс ID

Трейт возвращает URL авторизации (с `state` и PKCE `code_verifier`, которые хранятся в предсессии) и по `code` отдаёт нормализованный профиль: `provider`, `subject`, `email`, `name`. Таблица `external_identities(provider, subject) → user_id`. Endpoints Яндекса: `oauth.yandex.ru/authorize`, `oauth.yandex.ru/token`, профиль — `login.yandex.ru/info`. При совпадении email с существующим пользователем аккаунты не связываются автоматически (см. spec `identity-auth`): так закрывается захват учётки через чужой OAuth-аккаунт с тем же email.

### D6. Почта через outbox

Письма (подтверждение email, сброс пароля) пишутся в таблицу `jobs` в той же транзакции, что и бизнес-действие. Отправляет воркер через `lettre` (Rust) по SMTP с повторами и экспоненциальной паузой. Если почтовый сервис недоступен, регистрация не ломается.

**Провайдер — Yandex Cloud Postbox**, SMTP `postbox.cloud.yandex.net:587` (STARTTLS). Логин — идентификатор API-ключа сервисного аккаунта, пароль — секрет ключа.
- **Цена:** первые 2000 писем в месяц бесплатно, дальше около 80 ₽ за 1000 (тарифы Postbox на 15.09.2026). Наш объём — подтверждения и сбросы паролей, на порядки меньше.
- **Лимит:** квота по умолчанию — 1 письмо в секунду и суточный лимит, который поднимается через поддержку. Воркер почты отправляет не чаще 1 письма в секунду, остальное ждёт в `jobs`.
- **Отправитель:** `MAIL_FROM`, адрес в домене стенда. Отдельный поддомен изолирует репутацию отправки от остального домена.
- **DNS домена стенда.** Если имя стенда резолвится через wildcard-CNAME, ему нужна явная A-запись: у имени с CNAME не может быть TXT. Нужны:
  - `A <домен стенда>` → публичный IP сервера;
  - `TXT <домен стенда>` с SPF по инструкции Postbox;
  - `TXT postbox._domainkey.<домен стенда>` с публичным ключом DKIM (свой ключ, селектор `postbox`);
  - `TXT _dmarc.<домен стенда>` = `v=DMARC1; p=none; …` на время пилота, после проверки отчётов — `p=quarantine`.

Альтернативы:
- **Отправка напрямую с IP сервера.** Отклонена: у адресов из пулов провайдеров PTR вида `…pool.<провайдер>`, такие адреса получатели режут или кладут в спам, даже при открытом исходящем 25-м порту.
- **Stalwart (Rust) как свой MTA с relay через Postbox.** Отложена: доставляемость всё равно определяют IP Postbox. Подпись DKIM и очередь у нас уже есть (Postbox и outbox), а отдельный почтовый сервер — лишний компонент. Имеет смысл, если понадобится общий почтовый узел для нескольких сервисов или приём писем.
- **Unisender Go.** Рабочий вариант, но условия бесплатного тарифа проверить не удалось. Postbox прозрачнее по цене, а аккаунт Яндекса всё равно нужен для OAuth.

### D7. Фоновые задачи без брокера

Два механизма, оба на PostgreSQL:
- **Очередь `jobs`** (`SELECT … FOR UPDATE SKIP LOCKED`): письма, пересчёт связей антифрода, удаление просроченных сигналов. Повторы, `attempts`, `last_error`, идемпотентные обработчики.
- **Свиперы** — периодические циклы в процессе, каждые 15 секунд, под `pg_try_advisory_lock`, чтобы при нескольких экземплярах работал один:
  - автосдача попыток с `deadline_at < now()`;
  - применение расписания окон, а при закрытии — автосдача попыток без лимита времени;
  - очистка истёкших сессий и токенов.

Требование spec — автосдача не позже чем через минуту. Интервал 15 секунд даёт запас. При этом корректность ответов не зависит от свипера: сервер отклоняет ответ после `deadline_at` в момент сохранения. Альтернатива — `apalis`. Отложена: своя таблица на ~150 строк проще и прозрачнее, а при росте можно перейти.

### D8. Модель контента и блокировка

Таблицы: `courses`, `tests` (с колонкой `locked_at`), `questions`, `options` (с `is_correct`, `penalty`, `pinned`, `position`), `attachments`.

Блокировка: при сохранении ответа в той же транзакции выполняется `UPDATE tests SET locked_at = now() WHERE id = $1 AND locked_at IS NULL`. Чтобы не трогать строку теста на каждый ответ, у попытки есть флаг `lock_applied`, и UPDATE выполняется только при первом ответе попытки. Любая правка контента начинается с `SELECT … FROM tests WHERE id = $1 FOR UPDATE` и проверки `locked_at IS NULL`. Гонка «правка против первого ответа» сериализуется на строке теста.

Альтернатива — снапшоты версий теста. Отклонена: владелец выбрал запрет правок, а снапшоты усложнили бы модель без пользы для MVP.

### D9. Markdown и KaTeX рендерит клиент

Сервер хранит исходный текст. Клиент рендерит его через `markdown-it` с `html: false` (сырой HTML не интерпретируется), затем KaTeX через плагин. Ссылки получают `rel="noopener noreferrer"`. Плюс строгий CSP (`script-src 'self'`) как вторая линия защиты.

Альтернатива — рендер на сервере (`pulldown-cmark`). Тогда KaTeX пришлось бы тоже вызывать на сервере или вешать на клиенте поверх готового HTML. Рендер на клиенте даёт живой предпросмотр в редакторе той же функцией.

### D10. Картинки

1. Загрузка через приложение, multipart, лимит 10 МБ.
2. Декодирование крейтом `image`: так проверяется формат, а заодно отсекаются «бомбы» по размеру в пикселях.
3. Перекодирование в WebP (GIF остаётся как есть, если анимирован, но метаданные вырезаются). Перекодирование и удаляет EXIF.
4. Запись в S3 (Garage, D16) под случайным ключом.

Отдаёт картинки приложение через `/api/files/{id}` с проверкой прав (см. spec `access-control`), `Cache-Control: private, max-age=3600`. Альтернатива — presigned URL. Отклонена для MVP: ссылка живёт без проверки прав до истечения срока, а нагрузка на отдачу небольшая. Клиент S3 — `aws-sdk-s3` или `object_store`, за трейтом `BlobStore`. В тестах используется реализация в памяти.

### D11. Попытки

- `attempts`: `user_id`, `stream_id`, `started_at`, `deadline_at`, `submitted_at`, `submit_reason` (`manual` | `timeout` | `window_closed`), `layout` (jsonb: порядок вопросов и вариантов, фиксируется при старте), `current_index` для последовательного режима, `score`.
- Одна активная попытка: частичный уникальный индекс `(test_id, user_id) WHERE submitted_at IS NULL`. Лимит попыток проверяется под `pg_advisory_xact_lock(hash(test_id, user_id))`, чтобы две вкладки не начали две попытки одновременно.
- `deadline_at` = `started_at` + лимит, либо `NULL`, если лимита нет. Закрытие окна срок не меняет. Начало попытки проверяет, что окно открыто. Сохранение ответа проверяет только `deadline_at` и то, что попытка не сдана. Попытки с `deadline_at IS NULL` сдаются при закрытии окна (ручном или по расписанию) с `submit_reason = window_closed`.
- Разбор «после закрытия» открывается, когда окно закрыто и по паре «тест — поток» нет незавершённых попыток. Это точный запрос `NOT EXISTS (... submitted_at IS NULL)`. Из-за дорабатывающих попыток момент открытия разбора может наступить позже закрытия, и на панели студента он показывается как «после завершения всех попыток».
- Ответы: `answers(attempt_id, question_id, selected_option_ids, text, client_seq, saved_at, finalized)`. Клиент шлёт идемпотентный `PUT` с монотонным `client_seq`, сервер игнорирует запросы со старым `client_seq`, поэтому порядок доставки не важен. В последовательном режиме сервер принимает ответ только на вопрос `current_index`. Переход вперёд требует ответа и выставляет `finalized`.
- При сдаче доменная функция считает баллы, и они записываются в `answers.score` и `attempts.score`. Пересчёта нет: тест заблокирован.
- Клиент получает вопросы без `is_correct` и `penalty` — отдельные DTO на уровне типов. Разбор отдаётся отдельным эндпоинтом, который проверяет политику показа доменной функцией `review_allowed(policy, now, window_closed, active_attempts_in_stream, submitted)`.
- Офлайн: несохранённые ответы клиент хранит в IndexedDB и повторяет отправку. Индикатор «сохранено / не сохранено» показывается на каждом вопросе.

### D12. Оценивание в `domain`

`score_question(question, selection) -> Decimal` и `score_attempt(...) -> Decimal` реализуют формулы из spec `scoring` один в один. Покрытие:
- таблица примеров из spec;
- property-тесты (`proptest`): балл вопроса не больше W; пустой ответ даёт 0; балл попытки не меньше 0; в режиме «хотя бы один» с дефолтными штрафами выбор всех вариантов при наличии неверного даёт не больше 0.

### D13. Публикация за обратным прокси

Репозиторий содержит общий `deploy/compose/docker-compose.yml` без привязки к конкретному прокси. `app` публикует порт на `HTTP_BIND:HTTP_PORT` (по умолчанию `127.0.0.1:8080`), TLS завершает внешний прокси (Traefik, Caddy, nginx). Метки и сети конкретного прокси задаются в локальном `docker-compose.override.yml` рядом с `.env` стенда — он в репозиторий не попадает; пример для Traefik есть в `deploy/compose/README.md`.

- Аутентификация на прокси не нужна: у приложения своя, а студентам нужен прямой вход.
- `postgres`, `garage`, `backup-garage` и `backup` сидят только во внутренних сетях, без `ports:`. Это закрывает требование «Закрытые компоненты».
- Реальный IP клиента: приложение берёт IP из `X-Forwarded-For` **только** если запрос пришёл от адреса из `TRUSTED_PROXIES` (по умолчанию пусто). Иначе используется адрес TCP-соединения. Без этого антифрод можно обмануть подставным заголовком. При внедрении нужно проверить, что прокси видит реальные внешние адреса после NAT.
- Доступность проверяет внешний HTTP-монитор на `/health/ready`.

Альтернатива — TLS passthrough и терминация в приложении (её требует JA4). Отложена вместе с JA4 в backlog.

### D14. Антифрод

**Клиентский сборщик** — свой модуль. FingerprintJS v4 не берём из-за лицензии BSL, идеи v3 (MIT) использовать можно. Сборщик выдаёт три слоя:

1. **Браузер.**
   - Маркер: случайные 128 бит в cookie `zt_m` (не HttpOnly, годовой срок), в `localStorage` и в IndexedDB. Восстанавливается из любого уцелевшего хранилища.
   - Признаки конкретного браузера: UA, хеши canvas и audio, набор API.
2. **Устройство** — признаки, стабильные между браузерами одного устройства. Их выбор основан на работах по cross-browser fingerprinting:
   - `WEBGL_debug_renderer_info` (vendor/renderer, нормализуется до модели GPU) и лимиты WebGL: `MAX_TEXTURE_SIZE`, `MAX_VIEWPORT_DIMS`, набор расширений;
   - `screen.width/height`, `colorDepth`, `devicePixelRatio`;
   - `hardwareConcurrency`, `deviceMemory`;
   - набор шрифтов из фиксированного списка (~300), проверяется замером ширины текста;
   - `Intl` timezone, `navigator.languages`;
   - ОС и её версия из UA Client Hints или UA;
   - число медиаустройств по типам (`enumerateDevices` без разрешений).

   Отпечаток устройства — HMAC от нормализованного кортежа. Компоненты хранятся и по отдельности, чтобы считать частичное совпадение (Жаккар по шрифтам и расширениям).
3. **Поведение.** Динамика набора — интервалы удержания и между нажатиями, без кодов клавиш. Снимается в поле email на формах входа и регистрации и в свободных ответах. В поле пароля не снимается. Из этих данных строится вектор признаков: распределения интервалов по биграммам позиций.

**Хранение.** Сырые значения не хранятся. Сервер хранит HMAC-SHA256 каждого компонента с ключом из конфига: сравнивать можно, восстановить исходное из дампа базы нельзя. Числовые векторы динамики набора хранятся как есть, сами по себе они ничего не раскрывают. IP хранится как есть: он нужен для ASN, подсети и домашней сети. Срок хранения — из конфига, по умолчанию 365 дней.

**IP → ASN и страна.** Офлайн-база `iptoasn.com` (лицензия PDDL), еженедельное обновление задачей. Плюс список ASN хостингов и VPN. Признаки «хостинг/VPN» и «часовой пояс устройства не соответствует стране IP».

**Редкость.** Для каждого отпечатка устройства и IP считается, сколько разных аккаунтов его используют за 30 дней. Распространённый отпечаток (одинаковые ноутбуки класса) и IP общего пользования (больше 5 аккаунтов) ослабляют сигнал. «Домашняя сеть» — IP, которым пользовались не больше 3 аккаунтов, причём в разные дни.

**Граф и связи.** Вершины — аккаунты, маркеры, отпечатки устройств. Рёбра — наблюдения. Связь «аккаунт — аккаунт» выводится по путям в графе, включая транзитивные через общее устройство, и по прямым поведенческим совпадениям. Пересчёт делает задача в `jobs` при новом сигнале, результат — `identity_links(a, b, level, evidence jsonb, decided_by, decision, comment)`. Стартовые уровни задаются в конфиге и калибруются по решениям проверяющих:

| Сигнал | Уровень |
|---|---|
| общий маркер браузера | высокий |
| общий редкий отпечаток устройства | средний |
| общий распространённый отпечаток устройства | низкий |
| совпало только аппаратное ядро отпечатка (экран, процессор, ОС, часовой пояс) — похоже на другой браузер на том же компьютере; в граф устройств не входит | низкий |
| транзитивная связь через общее устройство | уровень самого слабого ребра пути |
| общая домашняя сеть в 2+ разных днях | средний |
| передача сессии: выход A → вход B в ≤ 5 мин из одной сети или с одного устройства | средний |
| идентичный нормализованный свободный ответ длиной от 20 символов | средний |
| совпадение наборов неверных ответов в 2+ тестах при 3+ ошибках | средний |
| близость векторов динамики набора выше порога на одном типе устройства | низкий (до калибровки) |
| регистрация по одной ссылке в ≤ 10 мин из одной сети + похожие email или имя | низкий |
| только IP общего пользования или подсеть | низкий, жёсткий потолок |

Два независимых сигнала среднего уровня поднимают связь до высокой. Кластеры для отображения собираются union-find по связям от среднего уровня и выше. В интерфейс уходит только `evidence` в человекочитаемом виде, без хешей.

**Чего не будет.** Два разных устройства без общей сети, общих аккаунтов и поведенческих совпадений технически не связываются. Это ограничение браузерной платформы, и объяснение в интерфейсе это прямо оговаривает.

Альтернативы:
- коммерческий сервис отпечатков — отклонён: данные студентов уходят третьей стороне, трансграничная передача, стоимость;
- сравнение паролей (несолёный HMAC пароля как сигнал «тот же человек») — отклонено: такой хеш подрывает защиту паролей из D4;
- WebRTC/STUN и JA4 — в backlog, им нужны правки инфраструктуры.

### D15. Аудит

`audit_log` — только INSERT. У роли приложения в базе нет прав `UPDATE` и `DELETE` на эту таблицу: это задаётся в миграции через `GRANT` и `REVOKE`, миграции выполняются отдельной ролью-владельцем. Отдельная таблица `attempt_events` пишется в той же транзакции, что и действие. События вкладки и связи клиент присылает батчами. Время событий — серверное.

### D16. Хранилище, развёртывание и бэкапы

**Garage вместо MinIO.** Garage (`dxflrs/garage:v2.4.1`) написан на Rust и лёгок в эксплуатации на одном узле. У MinIO community с октября 2025 нет готовых образов, а в 2026 репозиторий заархивирован, поэтому для нового проекта он не подходит. В приложении от S3 зависит только трейт `BlobStore`, а Garage поддерживает нужное подмножество S3 API.

Объёмы проекта — единицы гигабайт: основные данные живут на быстром диске, бэкапы — на отдельном (`BACKUP_DATA_DIR`).

`docker-compose.yml` (см. D13):
- `migrate` — тот же образ, команда `migrate`, запускается разово перед `app` (`service_completed_successfully`). Только у него есть пароль роли-владельца.
- `app` — один бинарь; при старте проверяет, что все миграции применены, и без них не запускается. Сеть `internal`, порт для прокси.
- `postgres` (17) — данные на основном диске (`data/postgres`). Сети `internal` и `backup` (для `archive_command`).
- `garage` — основное хранилище картинок, `metadata_dir` и `data_dir` на SSD, `db_engine = "lmdb"`, `replication_factor = 1`. Сеть `internal`.
- `backup-garage` — хранилище бэкапов. `metadata_dir` на основном диске (`data/backup-garage-meta`), `data_dir` на отдельном диске (`$BACKUP_DATA_DIR/garage-data`). Сеть только `backup`: у `app` нет ни маршрута туда, ни ключей.
- `backup` — образ с WAL-G и `rclone`, запускается разово. Сети `internal` и `backup`.

**«Кеш на SSD».** У Garage нет блочного кеша данных. Документация рекомендует держать метаданные на SSD, а данные можно хранить на HDD: тогда листинги, поиск объектов и учёт блоков идут с SSD, а HDD нагружается только последовательной записью и чтением блоков. Для бэкапов (почти только запись, чтение — при восстановлении) этого достаточно. Блочный кеш ядра (bcache/lvmcache) отклонён: он требует переразметки диска бэкапов и root-доступа.

**Бэкапы.**
- Postgres архивирует WAL через WAL-G (`archive_command`) в бакет `pg` на `backup-garage`.
- Раз в сутки — base backup WAL-G и `rclone sync` бакета картинок `garage → backup-garage`. Запускаются таймерами `systemctl --user` через `docker compose run --rm backup …`.
- Хранение 14 дней: `wal-g delete retain` и версионирование или очистка в бакете картинок.

**Защита от незамонтированного диска.** Перед стартом `backup-garage` и каждым прогоном скрипт проверяет точку монтирования (`BACKUP_MOUNTPOINT`, если задана) и файл-метку `$BACKUP_DATA_DIR/.zachteno-backup-volume`. Если что-то не так, прогон падает, push в мониторинг не уходит, и приходит тревога. Иначе при отвалившемся внешнем диске Garage тихо писал бы бэкапы в пустой каталог на основном.

**Проверка восстановления — еженедельно.** Временный контейнер Postgres восстанавливает последнюю копию из `backup-garage` и выполняет контрольный `SELECT`. Результат записывается в таблицу `ops_status` основной базы. Приложение отдаёт метрики `backup_last_success_timestamp` и `restore_check_last_success_timestamp`, при сбое пишет error-лог. Каждый успешный прогон бэкапа и проверки шлёт push в мониторинг (`BACKUP_PUSH_URL`, `RESTORE_PUSH_URL`), а отсутствие push вызывает тревогу. Процедура восстановления на момент времени описана в `docs/ops/restore.md`, для неё есть рецепт `just restore-pitr`.

Альтернатива — pgBackRest. Он мощнее, но тяжелее в настройке. WAL-G достаточно, и он работает с любым S3, включая Garage. Совместимость WAL-G с Garage (multipart, path-style) проверяется первым делом в задаче бэкапов.

### D17. Наблюдаемость

`tracing` + `tracing-subscriber` (JSON), `request_id` из `tower-http`. Метрики через `metrics` и `metrics-exporter-prometheus` на отдельном порту. `/health/live` и `/health/ready`, ready проверяет PG и S3. Пароли, токены, cookie и тексты ответов в логах не появляются: у чувствительных типов `Debug` вручную редактирует значение, а для тела запроса нет логирующего слоя.

### D18. Стратегия тестирования

- `domain`: unit- и property-тесты.
- `app`: интеграционные тесты через `#[sqlx::test]` на реальном Postgres (из `docker compose`). Они покрывают права доступа (матрица ролей против эндпоинтов), блокировку, лимиты попыток, сроки и CSV.
- `frontend`: `vitest` для утилит.
- Сквозные сценарии — Playwright против поднятого compose: регистрация по приглашению, прохождение с таймером и автосдачей, дорабатывание попытки после закрытия окна, выгрузка CSV, связь аккаунтов при смене браузера (два браузерных движка Playwright на одной машине).
- `just ci` прогоняет clippy, fmt-check, тесты бэкенда, проверку типов и тесты фронтенда, проверку актуальности OpenAPI-типов и `openspec validate --strict`.

## Risks / Trade-offs

- [Второй язык (TypeScript) во фронтенде] → Граница API строго типизирована генерацией из OpenAPI, бизнес-логика только на сервере. Фронтенд — тонкий слой отображения и ввода.
- [Argon2 с 64 МиБ съедает память под нагрузкой логинов] → Семафор на одновременные хеши, ограничение частоты входа, мониторинг RSS.
- [Ложные связи антифрода (общежитие, компьютерный класс)] → Потолок для IP-сигналов, только сигнал без санкций, ручное решение с комментарием, объяснение вместо «процента», калибровка весов по решениям проверяющих.
- [Отпечатки ненадёжны: Safari, Firefox и Brave рандомизируют canvas и WebGL или огрубляют их, инкогнито стирает маркер] → Отпечаток устройства строится в основном из признаков, которые браузеры почти не трогают (экран, ядра, шрифты, часовой пояс, ОС). Сравнение частичное, по компонентам, а не по одному хешу. Требование сформулировано как вероятностные сигналы.
- [Связь между разными устройствами строится только по сети и поведению и может не найтись] → Это ограничение платформы, и интерфейс его прямо оговаривает. Граф устройств связывает транзитивно, поэтому достаточно одного «моста» — общего устройства, сети или ответов.
- [Подмена `X-Forwarded-For` ломает сетевые сигналы] → Заголовок учитывается только от адресов из `TRUSTED_PROXIES` (D13).
- [Динамика набора на разных типах устройств (телефон и клавиатура) несопоставима] → Сравниваем только внутри одного типа устройства, уровень «низкий» до калибровки.
- [Персональные данные и 152-ФЗ не закрыты в MVP] → Решение владельца. Сигналы хранятся как HMAC с ограниченным сроком. Перед запуском на реальных студентах нужна консультация юриста (зафиксировано в proposal, Out of scope).
- [Один экземпляр приложения — точка отказа] → Бэкапы с PITR и проверкой восстановления. Приложение stateless, кроме in-memory rate limit, поэтому второй экземпляр добавляется переносом лимитов в PG.
- [Блокировка теста при первом ответе может застать методиста врасплох] → В редакторе виден статус «Заблокирован с …» и кнопка «Клонировать».
- [Письма уходят в спам] → Отправка через Postbox, а не с IP сервера. SPF, DKIM и DMARC на отдельном поддомене. Проверка заголовков `Authentication-Results` на ящиках Яндекса, Mail.ru и Gmail до пилота.
- [Postbox недоступен или исчерпана квота] → Outbox с повторами. Неподтверждённый email не мешает проходить тесты. В разделе суперпользователя видна очередь писем.
- [Бэкапы на том же сервере: пожар, кража или взлом хоста уничтожат и данные, и копии] → Копии на отдельном физическом диске защищают от отказа основного диска и от ошибок. `app` не видит хранилище бэкапов. Внешняя копия — в backlog (proposal).
- [Диск бэкапов отвалился или заполнился] → Проверка точки монтирования и метки перед каждым прогоном, контроль свободного места тем же скриптом. Отсутствие push даёт тревогу.
- [Недоступность Яндекс ID] → Вход паролем остаётся всегда. У суперпользователя пароль есть обязательно: его задают при создании через CLI.
- [Дорабатывающая попытка задерживает разбор «после закрытия» для всего потока] → Задержка не больше лимита времени теста. Попытки без лимита сдаются при закрытии окна, поэтому бесконечной задержки не бывает.

## Migration Plan

Greenfield, данных для миграции нет. Порядок запуска:
1. Поднять compose локально, выполнить `create-superuser`, пройти сценарии вручную и через Playwright.
2. Развернуть стенд по `deploy/compose/README.md`: `.env`, локальный override для прокси, `docker compose config`, затем `up -d`, проверить curl'ом. Добавить HTTP-монитор.
3. Настроить таймеры бэкапов, выполнить пробное восстановление по `docs/ops/restore.md`.
4. Зарегистрировать OAuth-приложение Яндекс ID с redirect URI `<PUBLIC_URL>/api/auth/oauth/yandex/callback` и настроить Postbox: адрес отправителя, DKIM, DNS-записи (D6). Проверить SPF, DKIM и DMARC на ящиках Яндекса, Mail.ru и Gmail.
5. Пилот на одном курсе и одном потоке.

Откат на этапе пилота — выключение сервиса. Данные остаются в бэкапах.
