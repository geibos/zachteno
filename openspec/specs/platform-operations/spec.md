# platform-operations Specification

## Purpose

Эксплуатационные гарантии сервиса: воспроизводимое развёртывание, резервное копирование базы и файлов с проверенным восстановлением, проверки состояния и наблюдаемость.

## Requirements

### Requirement: Развёртывание
Сервис SHALL разворачиваться одной командой из описания в репозитории: приложение, PostgreSQL и S3-совместимое хранилище. Все настройки и секреты задаются переменными окружения. Секреты MUST NOT храниться в репозитории. Миграции базы применяются автоматически при запуске приложения.

#### Scenario: Чистое развёртывание
- **WHEN** администратор на чистой машине заполняет файл окружения по образцу и выполняет команду развёртывания
- **THEN** поднимаются все компоненты, применяются миграции, и интерфейс открывается в браузере

### Requirement: Публичный адрес
Сервис SHALL быть доступен по HTTPS на публичном адресе стенда (`PUBLIC_URL`) без дополнительной внешней аутентификации перед приложением. HTTP MUST перенаправляться на HTTPS. Компоненты, кроме самого приложения (база данных, объектное хранилище), MUST NOT быть доступны из интернета.

#### Scenario: Открытие сервиса
- **WHEN** студент открывает адрес стенда из внешней сети
- **THEN** он видит страницу входа приложения по HTTPS с валидным сертификатом

#### Scenario: Закрытые компоненты
- **WHEN** кто-то из внешней сети пытается подключиться к PostgreSQL или к API объектного хранилища
- **THEN** соединение не устанавливается

### Requirement: Резервное копирование
Система SHALL обеспечивать резервное копирование PostgreSQL с восстановлением на любой момент времени: ежедневная полная копия и непрерывная архивация журнала транзакций. Объектное хранилище копируется ежедневно. Копии хранятся не меньше 14 дней на физическом диске, отдельном от диска с рабочими данными. Сервис приложения MUST NOT иметь сетевого доступа к хранилищу бэкапов и его учётных данных.

#### Scenario: Восстановление на момент времени
- **WHEN** в 14:05 по ошибке удалены данные
- **THEN** базу можно восстановить на состояние 14:04 по документированной процедуре

#### Scenario: Отказ основного диска
- **WHEN** диск с рабочими данными базы и картинок вышел из строя
- **THEN** базу и картинки можно восстановить с диска бэкапов на состояние не старше последнего архивированного сегмента журнала транзакций и последней ежедневной копии картинок

### Requirement: Проверка восстановления
Восстановление из резервной копии SHALL проверяться автоматически не реже раза в неделю: копия разворачивается во временный экземпляр, и на нём выполняется контрольный запрос. Неудачная проверка MUST быть видна администратору: в метрике и в логе с уровнем ошибки.

#### Scenario: Испорченная копия
- **WHEN** еженедельная проверка не может восстановить последнюю копию
- **THEN** метрика проверки восстановления показывает сбой, в логе появляется ошибка

### Requirement: Доставляемость писем
Служебные письма SHALL отправляться с адреса в домене стенда через транзакционный почтовый сервис, а не напрямую с IP-адреса сервера. Для домена MUST быть опубликованы SPF, DKIM и DMARC, и письма MUST проходить все три проверки у получателя. Скорость отправки MUST NOT превышать лимит почтового сервиса: ограничение соблюдает сам сервис отправки, письма сверх лимита ждут в очереди.

#### Scenario: Проверка подлинности у получателя
- **WHEN** пользователь с ящиком на Яндексе, Mail.ru или Gmail получает письмо подтверждения email
- **THEN** письмо лежит во «Входящих», а в заголовке `Authentication-Results` стоят `spf=pass`, `dkim=pass` и `dmarc=pass`

#### Scenario: Пик регистраций
- **WHEN** 50 студентов регистрируются по приглашению за одну минуту
- **THEN** все письма подтверждения уходят без ошибок превышения лимита, в порядке очереди

### Requirement: Наблюдаемость
Приложение SHALL писать структурные логи в JSON с идентификатором запроса, отдавать метрики в формате Prometheus и иметь эндпоинты liveness и readiness. Readiness проверяет доступность базы и объектного хранилища. Логи MUST NOT содержать пароли, токены, cookie сессий и содержимое ответов студентов.

#### Scenario: База недоступна
- **WHEN** PostgreSQL недоступна
- **THEN** readiness возвращает ошибку, а liveness — успех

#### Scenario: Логи входа
- **WHEN** пользователь входит по паролю
- **THEN** в логе есть запись о запросе, но нет пароля
